    allow, ask, deny and defaultMode

    The permissions block in .claude/settings.json holds three lists of rules and a start mode. A rule is a tool name, or a tool name with a pattern in brackets: Bash(npm run test *), Read(./.env), WebFetch(domain:docs.python.org). Deny wins over ask, and ask wins over allow.

    allow

    Claude Code uses these without asking. Bash(npm run test *) runs npm run test with any arguments. The older form Bash(npm run test:*) means the same. In a project file, allow rules take effect only after you accept the trust dialog for the folder.

    ask

    Claude Code asks you each time, even when an allow rule matches too. Use it for commands that are fine sometimes but leave your machine, such as Bash(git push *) or Bash(npm publish *).

    deny

    Claude Code never does these, and no allow or ask rule opens them again. Read(./.env) blocks the .env file in the project folder; Read(.env) blocks every .env, at any depth. A bare tool name such as WebFetch removes the tool.

    defaultMode

    The permission mode a new session starts in. A project's settings can set:

    • default: ask before edits and commands.
    • acceptEdits: edit files in the project without asking; still ask before other commands.
    • plan: read and plan, no edits.
    • dontAsk: never ask; refuse anything that would need your yes.

    bypassPermissions never asks. It does not take effect from a project's settings: set it in ~/.claude/settings.json, or start Claude Code in it. "disableBypassPermissionsMode": "disable" stops anyone from starting the project in it.

    A full settings.json example

    A project where Claude Code edits files and runs the tests on its own, asks before it pushes or publishes, and never touches secrets:

    {
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "defaultMode": "acceptEdits",
    "allow": [
      "Bash(npm run test *)",
      "Bash(npm run lint)",
      "Bash(git diff *)",
      "Bash(git commit *)",
      "WebFetch(domain:docs.python.org)"
    ],
    "ask": [
      "Bash(git push *)",
      "Bash(npm publish *)"
    ],
    "deny": [
      "Read(./.env)",
      "Edit(./.env)",
      "Read(secrets/**)",
      "Edit(secrets/**)",
      "Read(~/.ssh/**)",
      "Edit(~/.ssh/**)",
      "Bash(sudo *)"
    ],
    "disableBypassPermissionsMode": "disable"
  }
}

    How the rules work

    • Deny, then ask, then allow. The first match in that order decides. A narrow allow rule cannot open a hole in a broad deny rule.
    • A bare tool name such as WebFetch matches every use of the tool. In deny, it removes the tool from Claude Code.
    • Commands match the command text Claude Code is about to run. Claude Code splits &&, ; and pipes, and every part must match on its own. A trailing * also matches the bare command: Bash(npm test *) covers npm test.
    • Paths follow .gitignore patterns. A bare file name like .env matches at any depth. ~/.ssh/** is in your home folder. /src/** is src in the project, not on the disk root; write // for that.
    • Allow rules in a project file take effect only after you accept the trust dialog for the folder. Deny and ask rules apply at once.

    What these rules do not stop

    The rules bind Claude Code's own tools and the shell commands Claude Code recognizes, such as cat and sed. They do not bind a program that opens files by itself. A Python script can still read a denied .env. A deny rule for curl * does not stop /usr/bin/curl or sh -c 'curl …', and one for git push --force * does not stop git push origin main --force. For a hard limit on files and network, turn on Claude Code's sandbox. It applies the same limits to every command at the operating system level.

    With Angelia

    Angelia runs Claude Code for each WhatsApp or Telegram chat, in that chat's own profile folder. It writes the deny rules for you: angelia compile <profile> --write puts them into the profile's .claude/settings.json.

    • Every profile is denied, for reading and editing: your credential folders and files (~/.ssh, ~/.aws, ~/.gnupg, ~/.config/gh, ~/.netrc, ~/.npmrc, shell history and more); Angelia's own secrets; each CLI's transcripts; the other profiles' folders. A credential folder stays open only to a profile whose add_dirs names it.
    • A skill or MCP server the profile may not use is denied too. A denied skill is also taken out of the profile's skills folder, because a deny rule does not stop a skill typed as /name. Angelia removes only the links it made there; a denied skill you put there by hand stops compile until you move it.
    • Angelia changes only the entries it wrote. Your own rules in the same file stay.
    • Angelia starts no agent for a profile that was never compiled, or whose compiled deny rules were removed since.
    • The same limit applies: the rules hold the file tools, not every program. sandbox: true on a profile turns on Claude Code's sandbox for it.
