# Security model

Read this before giving a bot to anyone but yourself. An assistant that can read your files can be talked into reading them aloud.

- **Who can reach the agent.** Only chats listed in `routing.yaml`. A stranger who finds the bot and writes to it gets no reply; the daemon log gets one line with the chat id. In a group, only the owners are heard unless `allow_from` names others or says `"*"`, and only when they mention the bot (or reply to it). A group paired with `angelia init` admits only the person who paired it unless you say otherwise, and `check-config` names every group open to everyone. A sender who is not an owner gets `max_in_per_hour` messages to a profile in an hour (default 50); the rest are dropped with at most one line an hour, and only to a message that addresses the bot, so a flood cannot make the bot answer many times. The limit is per sender, not per chat: a group open to everyone lets N accounts send N times as much.
- **Who can act.** Tool permission replies, `/sh`, `/restart`, and any command that changes the session (`/new`, `/stop`, `/resume`, `/model`, `/effort`) are accepted from owners only. So are the CLI's own slash commands (`/clear`, `/add-dir`, a custom command): from anyone else, a message that starts with a slash reaches the agent as ordinary text. `agent_commands: [compact]` on a profile opens chosen ones to every member. `/help` and `/status` are open to anyone in the chat. In a DM the owner is the chat's user; in a group it is the `owners` list. A group member's `yes <id>` is refused, and their bare "yes" is a message like any other. `yes <id>` names its request outright. An owner's bare `yes` or `no` is taken as an answer only where it can be meant for nothing else: as a reply to the request's own message (matched by that message's id as the platform reports it, and only for a message Angelia sent; the quoted text is the sender's to write and picks nothing), or, with no reply, in a private chat or with a mention of the bot, and then only for the single open request, three seconds after it reached the chat. A bare word in a group with no mention, a reply to someone else's message, and "@someone yes" are messages, not answers. One gap stays open by design of the platforms: a word typed while the phone was offline is stamped when it is sent, so for three minutes after a request ended without the chat's answer no bare word is taken in that chat, and a request that was open beside it or asked in those minutes takes none for as long as it waits. A Telegram button answers only the request its message was sent for, whatever data the press carries, for an owner in the routing table (a channel's subscribers are not owners, and a channel gets no buttons).
- **What anyone the agent listens to can make it do.** Whatever its permission mode allows, with your files and your accounts: read a file and put it in the reply, run a tool the mode lets through, browse. The owner-only gates above keep the router's controls, not the agent's abilities. For a group, give the profile a cautious mode and list `allow_from`. An approval shows the whole command with its spacing collapsed; a long one is cut in the middle with the count of what is left out, and sent in full just before. In tmux mode too: the request comes from Claude Code's permission hook, never from the screen, where a command can draw a dialog of its own, and a yes answers that request and no other. A dialog only the screen shows is never answered from the chat.
- **What the agent can do** is the profile's `permission_mode`, exactly as in the CLI. `acceptEdits` asks before shell and risky tools; `bypassPermissions` never asks. `permissions` decides each request the mode would ask (reference, "Permission levels"): `refuse` refuses it without asking the chat, and the agent is told it is not permitted and answers in its own words; `ask` asks the chat, where only an owner's answer counts; `approve` runs it at once. Rules in Claude Code's syntax beat the default, refuse first, then ask, then approve; they are fixed patterns matched in code, and an unclear case never approves. Any approve, a default or one rule, is refused at load on a group where people other than the owners talk to the agent, unless the profile sets `unsafe_ok` (a sandbox does not count: what is still asked under one is mostly the way out of it). A shell approve rule passes only a plain line (no `;`, redirection, `$`, comment, glob or newline), and covers every argument of that command, including options that write files or run programs (`git log --output`, `git grep -O`, `find -exec`, `rg --pre`, `sort -o`, `tar`): approve only commands whose every option you accept; a shell refuse rule is best effort, since a shell has many ways to name a command, so a hard limit belongs in `deny` rules or the sandbox. A turn another profile started is never auto-approved. The older `permission_prompts: deny` is `permissions: refuse`. With `bypassPermissions` nothing is asked, so nothing is refused or approved by these rules, and `check-config` warns. A request from a turn that runs on in the background after a hand-off is not refused either: the chat is told to answer it in the Claude app or in its pane. Codex runs every command inside its own sandbox, enforced by the operating system: Angelia passes it the profile's deny rules and writable folders at launch, so a shell command cannot read a denied path either; it asks in the chat only for more access, such as one more folder for that turn, and a yes adds just that: the deny rules still hold. `sandbox: false` on the profile turns the sandbox off. `check-config` refuses a group open to every member on a bypass profile without the sandbox, warns when a group has no `allow_from`, when `/sh` is enabled on a group without owners, when `mention: any` puts every group message in front of the agent, when `permission_prompts: deny` or `permissions` sits on a bypass profile, and when a rule cannot be checked on the profile's backend.
- **Secrets.** The bot token and the secrets your capabilities use live in `~/.angelia/env` (mode 600). The daemon keeps them in memory: no agent, `/sh` or job gets the bot token, and each gets only the variables its own capabilities name. Every compiled profile denies its CLI's file tools the env file, the WhatsApp login (`wa/`, which is as good as the WhatsApp account), the API token, the tmux host files and the session map; your own credentials (`~/.ssh`, `~/.aws`, `gh`'s login, the Keychains folder, Mail and Messages, `.netrc` and the like, unless a profile names one in `add_dirs`); every CLI's record of past conversations, whatever the profile's own CLI (Claude Code's, Codex's, Grok Build's and pi's transcripts and prompt history, from every folder, your own terminal sessions included) and their user-level configs, whose MCP entries often hold a token; every other profile's folder (unless its own folder, `add_dirs` or a directory capability holds it); and edits to the files that decide its next launch. A deny stops the file tools and a plain `cat`, not a program that opens the file itself: an agent with a shell can read what you can read, so keep the shell asking in any profile other people can talk to, or set `sandbox: true` on it (below). `bypassPermissions` is refused on a directory containing `.env` or `secrets/` unless the profile says `unsafe_ok: true`.
- **The state folder is closed by default.** Every profile, on every backend, is denied everything in `~/.angelia` but the workspace, the logs and status, the API socket, the cache and agy folders (each held per profile), installed programs (`venvs`, `packages`, `node_modules`, `bin`), the owner's tool data in `data/` and the code clones in `projects/` (profiles read both today through their tools; per-profile rules for `data/` are a later change), and what the profile itself is given there: its folder, `add_dirs`, its allowed capabilities' folders, skills and secret files, each path exactly as named, and a capability's program (a server's command, or a command's first word or the script its interpreter runs) with the whole entry of the state folder it sits in. A path named in a text that is the state folder itself opens nothing. So passkeys, a payment ledger, `secrets/`, `keys/`, backups of `routing.yaml` and `sessions.json`, and any name the deny list does not know stay closed. A name made there after the last compile is closed at once in Angelia's own sandboxes (agy, pi's commands, sandboxed jobs, a grok copy for `angelia ask`) and in the daemon's own checks (send-media, an agy profile's `GEMINI.md` imports), and in a Claude Code or Codex profile's rules when its agent next starts: the daemon adds the deny rule to the profile's settings first (deny rules only, never a grant), as `angelia compile` would, and drops the rule of an entry that is gone. An agent never starts without every current floor rule: when that write fails, or a floor rule is still missing from its settings after it, the start is refused, whatever the agent did to the files in its own folder. Such an entry coming or going does not put a profile out of date for `angelia compile --check`. A profile added to the table (onboarding, a new agent) adds its deny rules to every other compiled profile at once. Every profile can read and write `~/.angelia/data`, whatever its tools: keep nothing there one profile must not see.
- **The sandbox.** `sandbox: true` on a Claude Code profile compiles the CLI's own sandbox on, with no unsandboxed escape. Measured with Claude Code 2.1.280, in `bypassPermissions` too: the deny rules then hold for every program the agent runs (a script that opens `~/.angelia/env` gets "Operation not permitted"), writes stay inside the profile folder and the temp folder, and the CLI's own settings files, skills and `.mcp.json` cannot be written at all. Network from the shell is blocked except the domains you list in `sandbox.network.allowedDomains` in the profile's `settings.local.json`; the CLI's web tools are not affected. Every compiled Claude profile already lets the sandbox reach Angelia's socket, so `angelia send` keeps working when you turn it on by hand.
- **agy (Antigravity CLI) is held by Angelia, not by itself.** Over ACP agy honours no allow or deny rule of its own (measured on agy 1.5.14, [ADR 0017](decisions/0017-agy-backend.md)), so Angelia holds both sides. Its gate answers every permission request agy sends (a write, an edit, a shell command, an MCP call) from the profile's rules, with pi's rules engine, and relays the rest to the chat. The whole agy process runs inside macOS's sandbox (`sandbox-exec`), made from the deny rules: a denied file is refused to agy's file tool and to every program it runs, reads inside the profile folder included, which agy never asks about. Writes are allowed only in the profile folder, its `add_dirs`, `_common`, agy's own folder in the state folder, the cache and temp; the other profiles' agy folders are closed. Nothing may be started outside the sandbox on agy's behalf (`open`, Apple Events). The sandbox opens one thing beyond pi's: the pseudo-terminal (`/dev/ptmx`, `/dev/ttys*`), without which agy cannot run any command. The keychain stays closed, and `/usr/bin/security` cannot be started: before each start the daemon copies your agy sign-in from the keychain into agy's own folder, where agy reads it. So no command agy runs can list or read your keychain items (Claude Code's, `gh`'s), but they can read agy's own Google sign-in in that folder. **This is a limit of the agy backend:** agy must read that file to work, and the network stays open, so any command agy runs can read the token and send it anywhere. The file holds your Google account's sign-in for agy: an OAuth access token, a long-lived refresh token and the account's email, with whatever access Antigravity asked for when you signed in (the file does not name the scopes). Whoever holds the refresh token can act as you towards Antigravity until you sign out of agy or revoke its access in your Google account. `/backend agy` says this too. Before each start the daemon also removes agy's `antigravity-cli/bin/` (its shell helpers, which must stay writable), and on stop it ends every process below agy, its commands' own sessions included. A command that detaches itself (`nohup ... &`) from a shell that has already ended is below nothing by then and keeps running until it ends, still inside the sandbox. In agy's folder its rules files, MCP config, plugins (`config/config.json`), skills and settings cannot be changed from inside, and agy does not start when they hold more than Angelia gave it. An owner's own Read and Edit rules in `.claude/settings.json` are read as Claude Code reads them (`//abs`, `~/x`, `x` and `./x` in the profile folder); `/x` is denied both in the profile folder and as an absolute path. This holds for pi too. Your own `~/.gemini` is closed to every agy profile; a profile on another backend keeps it open, so it can still run your own agy as a tool, which signs in and keeps its conversations there. Every profile, whatever its backend, is denied the agy folders in the state folder, where the profiles' conversations and sign-in copies are. Angelia never selects agy's `auto` mode, which runs commands unasked; `plan` is held by the gate, which refuses every edit and command, because agy's own plan mode is advice to the model only. `bypassPermissions` is the gate allowing all but what the rules deny. agy's web search (`search_web`) never asks either, in any mode, plan included (measured on agy 1.5.14), so no rule stops it: anything agy can read could leave in a search query. Claude Code's `WebSearch` asks, and a deny rule refuses it. Keep files you would not send to a search engine out of what an agy profile can read. Starting a subagent, a swarm, a workflow or a schedule never asks permission, so the gate cannot stop the start; the sandbox still covers all of them, since they run in agy's own process tree. A subagent's own requests do not reach the client by themselves, so Angelia finds the subagent's session (and a subagent's own subagent) and gates them like any other: during a turn they are asked in the chat, after the turn they are refused. A subagent Angelia cannot find is said in one line, and anything it asks cannot be approved. The generated `GEMINI.md` tells agy to do tool work itself, and every use of these tools is logged. agy refuses to start beside instructions or MCP servers Angelia did not give it. `sandbox: false` turns the sandbox off: then a Read deny inside the profile folder does not bind (agy reads there without asking), nor does any rule bind what a shell command reads; switching it off needs a compile, and a group open to every member then fails the load, as for Codex.
- **A loosened profile is not launched.** `angelia compile --write` keeps what it wrote for each profile in `~/.angelia/compiled/`, outside every profile. Before a session starts, the daemon checks the profile's settings against that: a profile never compiled, a deny rule that is gone, a settings file that no longer parses, or a sandbox turned off stops the launch, and the chat hears how to fix it (`angelia compile --write <profile>`). A rule a newer version adds is not a refusal: `check-config` names the profiles to compile again.
- **The daemon runs on the table the owner accepted.** The routing table sits in the workspace, which an agent can edit when the workspace is in its `add_dirs`: it could give itself a shell, add owners to a chat, point a capability at any program, or have onboarding hand strangers a profile. So a copy of the accepted table is kept in `~/.angelia/compiled/`, outside every profile, and the daemon and every job run on that copy. A table that changed since waits: `/restart` lists every change and restarts only on `/restart confirm`, which takes exactly the list shown (an edit made after you looked shows a new list). On the host, `angelia accept` takes the table (`--check` lists the changes). `angelia compile --write` works only from an accepted table and accepts nothing itself, so compiling one profile cannot carry in a change to another. Onboarding and `/backend`, which write the table themselves, refuse while it holds changes nobody accepted, and take only the change they made. `angelia jobs run` and `angelia pair` read the accepted table too. Only `model`, `effort`, `shell_timeout_seconds`, a route's `mention` and the idle, permission and stall timeouts need no confirm, and only when nothing else is waiting. The first start of a version with this takes the table as it stands. Not covered yet: what a profile's own `.claude/settings.local.json` allows (`permissions.allow`, `hooks`, `env`); Claude Code itself asks before an agent edits that file.
- **Connecting a set-up profile to a new chat.** `angelia profile connect <profile> whatsapp|telegram` arms a profile for the next new chat on that platform. Only an owner listed in `onboard.owners` uses the arm; `--owners` on an arm makes people owners of the new route, never people who may use an arm. The arm is used when that owner adds the bot to a group (the one who added it, as WhatsApp or Telegram reports it), or writes in a chat no route has (in a group, always mentioning the bot: the mention setting, `any` included, governs only the route's later messages). A stranger who adds the bot to a group, or writes there, cannot take the profile: nothing is routed, nothing is posted, and the arm stays. The arm is used once, holds for 24 hours (`--hours`, at most 168), and one profile at a time per platform. It lives in `~/.angelia/compiled/`, which no agent's file tools may open. `angelia profile connect` is a terminal command, with the same trust as `angelia profile add`: an agent with a shell that can run the CLI can run it too. So `--owners`, `--allow` and `--mention` are taken at once and set the new route (`--owners` adds to the `onboard:` block's owners, `--allow` replaces its `allow_from`), and the direct form `angelia profile connect <profile> whatsapp:<chat>` routes that chat with no arm and no owner's add or message. The command prints the new route's owners, allow list and mention when they differ from the `onboard:` block, so a widening is in plain sight. The owner's add or message rule above is about who uses an arm in a chat, not about who may run the command. A failed bind posts nothing in a group, so the others there learn nothing of the instance. The route is otherwise built from the `onboard:` block like onboarding's, on the accepted table only, and accepts nothing but that route. A profile with `shared_write` is refused.
- **Profiles talk to each other, and only by message.** An agent can ask another profile with `angelia turn <its chat> "<text>"` (or post there with `angelia send`); the message arrives labelled with the asking profile, never as you, and at most 30 an hour go from one chat to another. They share files through `workspace/_common/`, never by reading each other's folders. `workspace/_shared/` (the doctrine their instructions import) and `workspace/_capabilities/` (the skills and tools they run) reach every profile, so agents may read them but not edit them, except a profile with `shared_write: true`: give it to the one that keeps the instance. Claude Code's auto memory is off in every session Angelia starts: Claude keeps one memory folder per git repository, and every profile shares the workspace's, so each would load what the others saved; a profile keeps its memory in its own folder. `isolated: true` on a profile cuts it off from both: set it on a profile other people talk to, and `check-config` reminds you when a group is open to everyone.
- **The local API.** Each agent gets a token in `ANGELIA_API_TOKEN` that posts, attaches and types into its own chat, and messages other profiles as above; a prompt it types is plain text, never a CLI command. The owner token in `~/.angelia/api.token` reaches every chat. The file tools are denied it, but without a sandbox a program the agent runs can still open it, as with every file you can read. With the sandbox on, the deny floor holds for every command the agent runs, so its own token is the only one it has. That token attaches only what the agent's own file tools may read: the daemon opens an attachment itself, outside every sandbox, so a request made with an agent's token (`angelia send-media`, or a `MEDIA:` line) is held to that profile's deny rules, however the path is spelled. The reads a desktop app uses (chat history, settings, jobs, the event stream) and answering a permission prompt from it work with the owner token only; history is read by the CLI itself or from its own files, so Angelia keeps no copy of your messages.
- **Logs** hold chat ids, the ids of senders an allow list refused, session ids and counts, never tokens. A chat that is not allowed leaves at most one line per ten minutes, and `daemon.log` moves to `daemon.log.1` at 10 MB. One exception can carry message text: the last line of a failing CLI's error output. A direct chat sees it in the failure line too; a group sees only that the agent exited. The screen of a tmux pane that never reached a prompt goes to `~/.angelia/tui/<session>/screen.txt`, which agents cannot read. The same folder keeps two more screens, each overwritten by the next: `quiet-empty.txt`, of a turn that ended on an idle pane with no answer, and `idle-open.txt`, of a turn whose pane read idle while its transcript showed it open. Each can hold rows of the conversation, and Angelia does not delete a pane's folder.
- **Files from a chat.** Only a routed chat that passes its gate gets a file downloaded, up to 20 MB, under a name Angelia picks. Each profile's `.inbox/` is kept under 500 MB and 300 files, oldest out, and one sender gets 30 files an hour; past that the agent is told a file came and was not fetched.
- **Recent outgoing WhatsApp messages.** The daemon keeps its last hour (up to 500) in memory, never on disk, so a device that could not decrypt one gets the real message again.
- **Control characters.** Every incoming message is reduced to plain text before it reaches an agent, so no byte sequence in a message can act as a key press in a tmux pane.
- **What leaves your machine.** Every turn goes to the model provider of the CLI you chose (Anthropic for Claude Code, xAI for Grok Build, OpenAI for Codex, Google for agy), under that CLI's own terms. Telegram keeps bot messages on its servers; WhatsApp messages are end-to-end encrypted to the linked device. The workspace goes to a git remote only if you gave it one. Angelia itself sends nothing anywhere else: no telemetry, no update check, no account.
- **What it does not protect against.** Prompt injection in what the agent reads: a web page, a file or a forwarded message can still talk the agent into something its permission mode allows. Keep cautious modes for profiles that browse. Anyone you list as an owner has the agent's full powers in that chat. Sender display names are user-controlled and are passed to the agent in the message envelope, cleaned to one line. Another program running as your user can read everything the daemon can.
